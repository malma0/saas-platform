# Масштабирование БД — решения и план

Документ фиксирует решения по нагрузке на PostgreSQL: что уже сделано, что
осознанно отложено и при каком триггере к этому вернуться.

---

## 1. Защита от двойного бронирования — две независимые линии

**Линия 1 (приложение, первичная).** `ConflictChecker` + `SELECT ... FOR UPDATE`
внутри транзакции `CreateBooking`. Учитывает иерархию ресурсов (closure-таблица:
бронь зала конфликтует с бронью стола внутри) и активные holds.

**Линия 2 (БД, ремень безопасности).** Миграция
`2026_06_23_000001_add_overlap_exclusion_to_booking_resources` добавляет
`EXCLUDE USING gist` на `booking_resources`:

```sql
EXCLUDE USING gist (resource_id WITH =, tstzrange(start_at, end_at) WITH &&)
WHERE (status IN ('pending','confirmed') AND deleted_at IS NULL)
```

Время/статус брони денормализованы на `booking_resources` и поддерживаются в
синхроне двумя триггерами (`trg_br_sync_insert`, `trg_booking_propagate`) —
доменный код это не трогает.

**Что ловит:** пересечение по ОДНОМУ ресурсу при вставке в обход приложения
(прямой SQL, баг, второй сервис). Покрыто тестом `BookingOverlapConstraintTest`.

**Чего НЕ ловит (осознанно):** иерархические конфликты (зал vs стол) — это
остаётся за приложением через closure-таблицу. Дублировать иерархию в БД-констрейнт
несоразмерно сложно; линия 1 это уже закрывает.

## 2. Партиционирование `table_occupancy_sessions` — ОТЛОЖЕНО

**Почему отложено.** На момент написания анализатор (Python CV) не реализован
(~10%), таблица пустая. Партиционировать сейчас — преждевременно.

**Тонкость, из-за которой это не «просто добавить».** RANGE-партиционирование по
`start_at` требует включить ключ партиции во ВСЕ уникальные/PK-констрейнты.
Значит:
- `PRIMARY KEY (id)` → `PRIMARY KEY (id, start_at)`
- `UNIQUE (source, external_id)` → `UNIQUE (source, external_id, start_at)`

Последнее **ломает глобальную дедупликацию** по `external_id`: один и тот же факт
от анализатора, попавший в разные временные партиции, перестанет отсекаться. Это
реальный компромисс, а не формальность.

**Когда вернуться.** Как только анализатор начнёт писать в эту таблицу в
production-объёме (ориентир: > 5–10 млн строк или заметная деградация запросов
по `(resource_id, start_at)`).

**План на тот момент:**
1. RANGE-партиции по месяцам на `start_at`.
2. Дедуп `external_id` решать на уровне sync-job (проверка перед вставкой) либо
   уникальным индексом в пределах окна синхронизации, раз глобальный больше
   недоступен.
3. Политика хранения: горячие партиции на быстром диске, старые — архив/`DETACH`.
4. Автосоздание будущих партиций (pg_partman или cron-команда artisan).

## 3. Прочие ориентиры роста (в порядке появления)

| Узкое место | Когда | Решение |
|---|---|---|
| Тяжёлые отчёты/агрегации | десятки тысяч броней | read-replica или materialized views |
| Рост `activity_log` (spatie) | постоянно | retention-джоба, чистка старого |
| Конкуренция на горячих слотах | пиковые продажи | линия 2 уже снимает риск корректности; следить за временем удержания блокировок |

---

## 4. Что НЕ является узким местом

Архитектура уже избегает типичных ошибок, убивающих рост: PostgreSQL (не SQLite),
деньги в `bigInteger` minor units (не float), время в `timestampTz` UTC,
мультитенантность по `club_id` с составными индексами под горячие запросы,
closure-таблица для иерархии, ULID для внешних идентификаторов.
